## 2. Detailed PRD — Top 3 P0 Features (currently MISSING)

> RBAC enforcement (#4) is P0 but classified **exists-enhance** (wire `lib/rbac.ts` into a shared route guard, ~1 file), so it is excluded from the "missing" deep-dives below and tracked as a standing security task. It ships alongside #1–#3 and every new route below must call the guard.

### P0-1 · Whitelisting / Paid-Amplification Media Manager

**Problem statement.** The agency's highest-margin, highest-retention product is paid creator amplification — Spark Ads (TikTok) and Partnership Ads (Meta) run through the brand's own ad account. Today the agency tracks ad-account access grants, creator content/post IDs, partnership-ad codes, spend caps, and flight dates across a dozen Business Manager logins in spreadsheets. An expired partnership code or a creator revoking authorization mid-flight kills a live paid campaign, and the brand notices before the agency does. Nothing in our codebase models any of this.

**User stories.**
- As a media buyer, I add a paid-amplification record to an activation with the ad account, partnership/Spark code, content ID, spend cap, and flight window, so it lives beside the campaign, not in a spreadsheet.
- As a media buyer, I get alerted before a code/authorization expires or when a creator revokes access, so I fix it before the brand sees a dark campaign.
- As an agency lead, I see every live amplification across clients with status (pending/granted/revoked/expired) and remaining spend headroom in one view.
- As a creator (portal), I see which of my posts a brand is authorized to amplify, for how long — and if a request exceeds what I signed, it's blocked pending an added-fee amendment (ties to P0-2).

**Acceptance criteria.**
- New record captures: `platform` (reuse `Platform` enum), `adAccountId`, `businessManagerId`, `authCode` (Spark/partnership), `contentId`/postId, `spendCap`, `spentToDate`, `flightStart`, `flightEnd`, `status` enum (`PENDING`/`GRANTED`/`REVOKED`/`EXPIRED`), FKs to `Campaign`, `Activation`, `Creator`.
- Records surface as a new sub-tab on the campaign detail page (same pattern as existing posts/deposits/negotiations/payout-requests sub-tabs).
- A cron (new `app/api/cron/check-amplification`, mirroring `app/api/cron/sync-posts`) flags records where `flightEnd` is within N days or `status=EXPIRED`, writing an in-app notification (`Conversation`/`Message` or `ActivityLog`) — **email is opt-in and gated**.
- A whitelisting request whose scope/window exceeds the creator's signed `UsageRight` (P0-2) is rejected at the API with a clear reason.
- All new routes call the shared RBAC guard (#4); only roles with `campaigns:*` write.
- **v1 is a structured tracker + alerts entered manually.** Live sync/read-back from Meta/TikTok Business Manager is out of scope (gated).

**Data-model / API touchpoints.**
- **New model** `PaidAmplification` (FKs: `campaignId`, `activationId`, `creatorId`; reuses `Platform`). **New enum** `AmplificationStatus`.
- **New routes** `app/api/campaigns/[id]/amplification` (GET/POST/PATCH), `app/api/cron/check-amplification`.
- **Reuses** campaign-detail sub-tab UI, `ActivityLog`/`Conversation` for alerts, `lib/rbac.ts` guard, existing cron registration pattern.

**Out of scope.** Automated Spark/partnership code *provisioning* via Meta/TikTok Marketing APIs; reading live spend/delivery from ad accounts; ad-creative optimization; billing the media markup (that's the payments layer, already solid).

**Gated:** `CREDS` (live Business-Manager sync — parked), `EMAIL` (expiry alerts — in-app by default, email parked), `PROD` (migration).

### P0-2 · Usage-Rights & Contract Ledger

**Problem statement.** Usage rights, territory, exclusivity windows, and license duration live as prose in individual creator contracts. Brands run whitelisted content past its licensed window; creators discover their content running as paid media with no added fee; and when a brand asks mid-campaign "can we also run this on a billboard," nobody answers without re-reading the PDF. This is the most common legal-exposure and client-escalation source in the business, and it's the creator's single largest requested feature (their "Usage Rights & Whitelisting Ledger," sized L). We have a `Document` model for the signed file but no structured license terms.

**User stories.**
- As agency ops, I record structured usage terms per deliverable — channels, territory, exclusivity, license start/end, fee — and attach the signed PDF, so the answer to "what did we license" is a lookup, not a re-read.
- As agency ops, I get an expiry dashboard and alerts, so a lapsing license becomes a proactive re-license upsell instead of a takedown scramble.
- As a creator (portal), I see exactly what each brand licensed and for how long; a request beyond my signed scope requires an added-fee amendment before it's allowed.
- As legal, I can answer a channel-extension request ("billboard/CTV/email") against structured data in seconds.

**Acceptance criteria.**
- New record captures: `channels` (multi-select: `ORGANIC`/`PAID_SOCIAL`/`OOH`/`CTV`/`EMAIL`/`WEB`), `territory`, `exclusivity` (bool + scope), `licenseStart`, `licenseEnd`, `feeAmount`+`currency` (reuse `Currency` enum), `status`, FKs to `Campaign`/`Activation`/`Creator`, and `documentId` → existing `Document`.
- Expiry cron (new `app/api/cron/check-usage-expiry`, same pattern as P0-1) surfaces licenses expiring within N days on an org dashboard panel and in the creator portal.
- P0-1 amplification requests validate against the matching `UsageRight` (paid-social channel present + within window); mismatch is blocked with the specific shortfall named.
- Creator portal renders a per-creator usage ledger (new page under existing `app/(portal)` surface).
- Routes enforce the RBAC guard.
- **v1 terms are entered as structured fields manually.** AI extraction of terms from an uploaded PDF is a fast-follow (see gated).

**Data-model / API touchpoints.**
- **New model** `UsageRight` (FKs `campaignId`/`activationId`/`creatorId`/`documentId`; reuses `Currency`). **New enums** `UsageChannel`, `UsageRightStatus`.
- **New routes** `app/api/campaigns/[id]/usage-rights` (CRUD), portal read route under `app/api/portal/*`, `app/api/cron/check-usage-expiry`.
- **Reuses** `Document` (PDF storage), `Currency`, alert/cron pattern, `lib/rbac.ts`. Optional fast-follow reuses the **already-wired, metered** Anthropic path (`lib/ai/metering/usage.ts`, `lib/negotiation/claude.ts` pattern) to parse PDF → structured terms.

**Out of scope.** E-signature / contract execution; a contract authoring/templating tool; the AI clause-extractor in v1 (structured manual entry first); cross-org license sharing.

**Gated:** `EMAIL` (expiry alerts — in-app default, email parked), `SPEND` (optional AI clause-extraction — incremental Anthropic cost, already metered, still parked as fast-follow), `PROD` (migration).

### P0-3 · Conversion & ROI Attribution

**Problem statement.** Renewal conversations die when the agency presents reach/engagement and the brand's CFO asks about CAC and incremental revenue. Every brand's internal stack (Shopify, GA4, BI) speaks a different attribution language than "creator reach." Our reporting surface is **solid** (`Report` model, share tokens, PDF via `@react-pdf/renderer`, `lib/metrics` computing EMV/benchmarks/cost-per) — but there is no data layer tying a creator/campaign to actual clicks, orders, and revenue. This feature adds that layer and pipes it into the existing dashboard, so the client's boss opens a live branded report showing ROAS/CAC without emailing us.

**User stories.**
- As an AM, I generate a trackable link and/or a unique promo code per creator per campaign, so clicks and orders attribute back to the exact creator.
- As an AM, conversions land against the right creator/campaign (via promo code, UTM, or a posted webhook), so I don't reconcile by hand.
- As a brand director, I open one branded live report (existing share-token flow) showing spend, revenue, ROAS, and CAC — not just views — so I can justify next quarter's budget before the QBR.
- As an agency lead, I see attributed revenue per campaign/creator feeding the existing financial dashboards.

**Acceptance criteria.**
- Trackable link: public redirect route `app/(public)/go/[slug]` (mirrors existing public routes `/share/[token]`, `/explore/[slug]`, `/kit/[token]`) records a click then 302s to `destinationUrl`.
- Promo code: unique code per activation/creator, matched on inbound conversions.
- Conversion ingest via **(a)** authenticated webhook `app/api/webhooks/conversions` reusing the **existing** HMAC + replay-safety pattern (`PaymentWebhookEvent`, `PaymentIdempotencyKey`, `lib/payments/webhookLog.ts`), and **(b)** manual CSV import (reuse existing export/import plumbing).
- Attributed revenue flows into `lib/metrics/*` and `CampaignFinancials`, and renders in the existing `Report` share page + PDF and `/api/campaigns/[id]/performance` — ROAS and CAC appear as first-class metrics.
- v1 attribution model is **last-touch** via link/code; no multi-touch modeling.
- Routes enforce the RBAC guard; the public redirect and webhook are the only unauthenticated surfaces and are rate-limited (`lib/rateLimit.ts`).

**Data-model / API touchpoints.**
- **New models** `TrackedLink` (FKs `campaignId`/`activationId`/`creatorId`, `slug`, `destinationUrl`, `clicks`), `Conversion` (FK `trackedLinkId`/`campaignId`/`creatorId`, `orderValue`, `currency`, `source` enum `PROMO_CODE`/`UTM`/`WEBHOOK`/`MANUAL`, `externalId`, `occurredAt`), optional `promoCode` field on `Activation`. **New enum** `ConversionSource`.
- **New routes** `app/(public)/go/[slug]`, `app/api/webhooks/conversions`, `app/api/campaigns/[id]/conversions` (list/import).
- **Reuses** `Report` + `lib/reports/CampaignPerformancePDF.tsx`, `lib/metrics/{emv,benchmarks,costs}.ts`, `CampaignFinancials`, `lib/payments/{idempotency,webhookLog}.ts`, `lib/rateLimit.ts`, `lib/rbac.ts`.

**Out of scope.** Native Shopify/GA4/e-commerce OAuth connectors (gated — v1 uses promo codes + UTM links + generic webhook/CSV); multi-touch or incrementality/holdout modeling; a first-party server-side pixel beyond the simple authenticated webhook; identity resolution across devices.

**Gated:** `PROD` (public redirect + public webhook endpoint live on prod; migration), `CREDS`/`SPEND` (Shopify/GA4 connectors — parked to a later cycle).
