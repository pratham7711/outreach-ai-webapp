Frontend performance benchmarks

Every main screen, loaded and then used, against the published "good" thresholds. The first-load and responsiveness budgets now pass on every page in every theme. Three interactions still produce one long task just over RAIL's 50 ms.

01The budgets

Each threshold is the published boundary of "good", not a number picked to pass. Core Web Vitals are judged at the 75th percentile of real visits. A lab run is one visit on a fixed profile, so the profile below is set deliberately slower than a typical desktop.

02How it was measured

  • Builds. Plain next build + next start for both sides: before is commit 0d0a7af, after is the same commit with this change. The two ran back to back in each theme, so neither had a warmer machine.
  • Profile. CPU slowed 4×, 40 ms round trip, 10 Mbps. Responses are brotli-compressed by a local proxy, as Vercel's edge does; without it, uncompressed JavaScript adds 300–600 ms to LCP that production does not have.
  • Screen. 1440 × 900, Chrome, signed in, in the light, dark and creatorcore themes.
  • Data. Synthetic and production-sized, on a throwaway local Postgres: an 800-post campaign, a 300-creator list, 1,700 creators, 480 campaigns. No real creator data.
  • Use. 8 of the pages are also used after loading: typing in search, switching tabs, toggling list/table view, sorting a column, ticking a row, changing the date range. INP and "longest task in use" come from these.
  • Collection. Google's web-vitals library for LCP, FCP, CLS, INP and TTFB. Long-task and event-timing observers for TBT (sum of each task's time over 50 ms, from first paint to settled) and for the longest task during use.

05What was fixed

  1. One CSS pattern made every DOM change restyle the whole page

    Five rules styled elements below a :has(): three page-layout rules in globals.css, and two Tailwind variants in avatar-group and alert components that nothing renders. Tailwind emitted their CSS anyway. With any of them present, alongside a :has() that can match deep in the tree, Chrome restyles the entire document whenever a node is inserted anywhere. The creator list inserts one each time an avatar falls back to initials. Each rule is now a plain class on the element, and a unit test fails if the pattern returns.

    Style recalculation per inserted node on the 300-row list (9,318 elements): 15 ms (20 ms in creatorcore) → 0.4–0.6 ms. Each rule alone cost 0.2 ms, which is why none looked guilty on its own. List-page blocking time 1,093–1,347 ms → 66–68 ms, together with fix 2.

  2. Off-screen rate-card rows are skipped until scrolled to

    The list's rate-card rows use content-visibility: auto, so the browser lays out and paints only the rows on screen. The placeholder height is the row's content box, padding and border excluded. Sized from the outer box, the scroll height drifted by about 6,700 px.

    Scroll heights identical before and after in 15 of 15 width and theme combinations. Row geometry, colour and text identical in 27 of 27.

  3. The campaign's Creator Performance chart shows the top 10

    The chart drew a pair of bars for every creator: 240 bars and 120 labels in a 240 px card on a 120-creator campaign. That was unreadable, and the chart library measured every label in the DOM in one 290 ms task. It now draws the ten creators with the most views and says so under the title.

    Campaign analytics tab blocking time 208–260 ms → 96–108 ms across the three themes.

  4. Sorting posts parses each date once, not on every comparison

    The posts table computed both sort keys inside the comparator, which is about 2 × n log n date parses. It now computes one key per row, sorts the pairs and unwraps them.

    Old and new sort compared on 2,000 random arrays in both directions, with ties, invalid dates and ±Infinity among the keys: identical order every time.

  5. Re-render fixes from the earlier pass

    List rows are memoised components. Number and date formatters are built once rather than per cell. Chart entry animations are off on 27 series. Page-entry animations run 0.15 s with no stagger. The campaign navigation context is split so publishing a tab does not re-render its readers. Avatars load lazily.

06What is still over, and why it stays

After the fix: /campaigns/[id] 57 ms, /campaigns/[id]?section=posts 61 ms, /analytics 52 ms. Each is a single task when a click mounts a new view: the campaign tabs, the posts list view, and the analytics range and tab. INP on those same clicks stays at or under 96 ms, against a 200 ms budget: under half the allowed time.

Profiling puts most of each task in React creating the new view's DOM, about 14–17 ms unthrottled. Getting under 50 ms at 4× CPU would mean virtualising or splitting those views across frames. That is a redesign of working screens to win a few milliseconds on the strictest guideline, so it is not in this change.

07What looks different

One thing. The Creator Performance chart on a campaign's analytics tab shows the top 10 creators by views, with "Top 10 of n creators, by views" under the title once a campaign has more than ten. Everything else was compared pixel by pixel: 10 pages in all three themes at desktop width, and 21 page-and-theme combinations at 390 px. Apart from anti-aliasing on one search icon, they are identical.

08What this does not cover

  • TTFB. A local server answers in about 10 ms, which says nothing about production. Production /login measured 846 ms on a cold start and 240–280 ms warm. The cold figure is over the 800 ms budget, and it is server start-up, not the frontend.
  • Real visits. These are lab runs on one profile. The budgets are defined at the 75th percentile of real visits, which need field data from production to confirm.
