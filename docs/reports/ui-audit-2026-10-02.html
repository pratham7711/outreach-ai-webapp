01Why CreatorCore felt slow

Two CreatorCore rules had the shape :root.creatorcore .cc-shell-root:has(.cc-sidebar-rail[data-shell="dashboard"]) .cc-tab-count: a :has() on the whole shell with a descendant after it. Taking out just those two rules brought /campaigns from 667 ms to 73 ms. ● The likely mechanism is that Chrome re-checks that pattern across the whole shell whenever anything inside it changes, and the app changes the DOM constantly: typing, hover cards, toasts, live counts. ○ Every such rule starts with :root.creatorcore, so Light and Dark never match them. They measured 44–50 ms on the same pages before the fix. ●

The fix puts the shell kind on the root element as an attribute, data-shell, set by components/layout/ShellRoot.tsx, and the rules select on that. A computed-style comparison of the old rules against the new ones, on 40 pages, found 0 differences. ●

05Decisions for you

  1. CC-09, the table bleed. In CreatorCore the list tables extend past the page column: 20 px left and 24 px right at 1440, 22 px each side at 1000. That copies CreatorCore's own list pages. On list detail and /admin it reads as a table running off the page. Keep it, or limit the bleed to the screens it was measured on?
  2. Doubled card padding, app-wide. 34 cards set 24 px of padding on top of the 24 px the card component already adds, so their content sits 48 px in. This batch fixes it on the campaign Overview only. Fixing it everywhere changes the look of most pages, so it needs your yes.
  3. CC-11, the settings zoom jump. CreatorCore zooms its pages to 90% from 1280 to 1600 px and 85% from 1024 to 1280, but not its settings pages, so the sidebar grows about 11% on entering settings. That matches CreatorCore exactly. Keep the match, or smooth it?
  4. D03, Dark charts in greys. Dark draws series in greys told apart by dash pattern. That is deliberate, but neighbouring greys are close. Add one accent, or keep it monochrome?
  5. The zero-follower guard (section 06) is ready and not in this batch, because it needs its own yes.

06Trackers and zero readings

Are all creator trackers live? No. Each sweep reads most creators, but some fail every time. The three causes are an Instagram rate limit, an account that no longer exists, and an Instagram account that is not a professional account. A sweep also stops at 400 creators, so anything beyond that never shows in the logs. Exact counts come from a read-only query you run; they are given in the session, not here, because this repository is public. ○

Why some creators now read 0 followers. The older sweep, still the one writing on production, has no check for "fell to zero". TikTok sometimes serves a page with zeroed figures, the parser accepts 0 as a reading, and the sweep stores it. ● in code; whether TikTok or the account caused a given zero is unverified.

What it does to client tracking: charts show a drop to zero for up to 30 days; the change column shows −100%, and later a false gain the size of the whole audience; shared lists show "—" and a minimum-followers filter hides the creator. The headline figure recovers on the next good reading, but the history does not. ○

The fix, ready but not in this batch: both readers refuse a drop to zero, judged against the last non-zero reading, and so does the canary. The tracker chart and the change figure skip zeros already stored. It comes with nine tests. Repairing the zeros already stored is a production write, so it is yours to run. ○

07How this was checked

  • Every change was built as a production build and served locally against a throwaway Postgres in Docker, seeded with a test organisation. Nothing touched the production database. ●
  • Each fix was measured in Chrome in all three themes at 1440, 1000 and 390 px: element sizes, computed styles and overflow, plus screenshots. Across all of them: no page errors, and no horizontal page scroll. ●
  • The contrast suite passes (4 of 4). 19 low-contrast pairs it had on record no longer occur, so its CreatorCore debt list went from 114 entries to 95. ●
  • Type check passes, and lint finds no problems in the changed files that were not there before. ●
  • The deploy gate's unit, build and full Playwright suites run on the commit that contains this report. Their results are given in the session, because writing them here would change the code they certify.
