Site audit — lag and skeletons

campaign.madeboring.com · 2026-11-19 (IST) · deployment dpl_AswdmZ3R4paC2MesAqhNChds7rbn · measured with the Review Demo agency account in headless Chrome 1440×900

Verdict

  1. The lag you feel on clicks is a freeze, not a slow server. On 8 of 11 sidebar destinations no skeleton appears: the old page stays on screen, unresponsive-looking, until the new one is ready (330–440 ms on this small account; it grows with an org's data). Only /campaigns and /trackers show their skeleton instantly (35–41 ms); /settings/api-keys shows one after 191 ms.
  2. Skeletons are wrong on every detail page and every route without its own skeleton. A campaign opens with the campaign list skeleton; song, list and creator pages get list or dashboard shapes; calendar, analytics and settings get the dashboard shape. Several then show a second, different skeleton from inside the page.
  3. List skeletons omit the tab strip and header band, so content jumps ~50 px when the page arrives (campaigns, trackers, creators, dashboard).
  4. The dashboard jumps after it loads (CLS 0.10, the "needs improvement" line): tiles grow 98→128 px when financials arrive, and /api/dashboard/financials is requested twice on every visit.
  5. Server response is not the bottleneck at this account's size: TTFB 88–152 ms on every route. At LKM's size (hundreds of campaigns, thousands of posts) it is not measured — see "Not measured".

Fix plan (in this order)

  1. Make skeletons show on every click — find why 8 routes skip their loading boundary on client navigation and fix it at the root, so a click always answers within one frame.
  2. One skeleton per page type, shared with the page — detail routes (campaign, post, creator, list, song) get their own loading.tsx that renders the same component the page shows while it fetches, so the hand-off is seamless and there is no second skeleton.
  3. Neutral group fallback — header + one content block instead of the dashboard shape; calendar gets a month-grid skeleton.
  4. Header band + tabs in the skeleton — PageHeaderSkeleton draws the band hairline and an optional tab strip; used by campaigns, trackers, creators, dashboard.
  5. Per-page card skeletons for songs, lists, plans, creators; correct wrapper (rsp-page) and counts.
  6. Dashboard — reserve the tile sub-line so tiles don't grow; one financials request instead of two; chart skeleton at its real 400 px.
  7. API keys — reserve the block that pushes the card down.
  8. Measure at LKM scale on a copy of the data (never prod), then fix whatever query or render dominates there.

Not measured

  • LKM-sized data on prod. The review account has 1 campaign and 2 posts. Vercel's logs don't record durations, and reading LKM's org on prod is off limits, so server and render cost at their size is unknown until it is measured on a copy.
  • Phones on real networks (only CPU throttling, desktop network).
  • Code-audit rows marked “code” were read, not all seen in a browser.
