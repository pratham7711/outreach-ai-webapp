# Sound worker — the audio tracker's reader

The one part of this product that cannot run on Vercel.

## Why it exists

A TikTok music page has no count in its HTML. TikTok stopped server-rendering
them; the number arrives from `/api/music/detail/`, which answers 200 with an
empty body unless the request carries `X-Bogus`, `X-Gnarly`, `X-Dynosaur` and
`msToken`. Those are generated by TikTok's own client script while the page
loads, and a server cannot forge them. So the reader has to be a real browser.

It also has to be outside India. From an Indian IP, `tiktok.com` returns an
"About | TikTok" placeholder and the app never boots, so a browser there reads
nothing either — a plain `fetch` gets `ECONNRESET`.

That is the whole reason for a separate box: a browser, somewhere TikTok will
talk to.

## What it does and does not hold

It holds `APP_URL` and one token. It does **not** get `DATABASE_URL`.

The worker reads a number and posts it. Every decision about what that number
means — the 24-hour delta, the velocity score, backfilling a sound's title and
cover — happens in the app, in `recordSoundSnapshot`, the same function the cron
and the in-app Refresh button call. That is deliberate: the last time this
arithmetic existed in two places, one copy put a percentage into
`videosAdded24h` and a sound with 46 uses reported "+100 videos added".

Keeping the database out of reach also means a box whose job is pointing a
browser at a hostile page never holds credentials to the database production
runs on.

## Requirements

- Any Linux VPS **outside India**. It needs ~1 GB RAM and no GPU; the smallest
  tier anywhere is enough. Check the region before you provision: an Oracle
  Cloud or AWS instance in Mumbai or Hyderabad is subject to the same block as a
  laptop in Bangalore, and will read nothing.
- Node 20+.

## Install

```bash
# 1. Copy the two directories it needs. The worker imports the browser reader
#    from ../dev, so keep the layout.
ssh you@vps 'mkdir -p /opt/outreach-sound-worker'
scp -r scripts/sound-worker scripts/dev you@vps:/opt/outreach-sound-worker/

# 2. Install just Playwright and its browser. Not the app's dependencies --
#    this needs one package.
ssh you@vps
cd /opt/outreach-sound-worker/sound-worker
npm install --omit=dev
npx playwright install --with-deps chromium

# 3. The token and the app it reports to.
sudo tee /etc/outreach-sound-worker.env >/dev/null <<'ENV'
APP_URL=https://campaign.madeboring.com
SOUND_INGEST_TOKEN=<paste it here>
ENV
sudo chmod 600 /etc/outreach-sound-worker.env
```

`SOUND_INGEST_TOKEN` is a Vercel environment variable you set on the project. If
it is absent the endpoint falls back to `CRON_SECRET`, which works immediately
but hands this box a secret that also triggers every cron — so set the dedicated
one before pointing anything real at it.

## Check it before scheduling it

```bash
cd /opt/outreach-sound-worker/sound-worker
APP_URL=... SOUND_INGEST_TOKEN=... node read-sounds.mjs --dry-run
```

`--dry-run` reads every page for real and writes nothing. Expect a line per
sound and a summary. If every sound says `MISS`, the box is almost certainly in
a blocked region — confirm with `curl -s https://www.tiktok.com/ | grep -o
'<title>[^<]*'`, which returns `About | TikTok` where it is blocked.

## Schedule

```bash
sudo useradd --system --home /opt/outreach-sound-worker --shell /usr/sbin/nologin sounds
sudo chown -R sounds:sounds /opt/outreach-sound-worker
sudo cp outreach-sounds.service outreach-sounds.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now outreach-sounds.timer

systemctl list-timers outreach-sounds.timer   # when it next fires
journalctl -u outreach-sounds.service -n 50   # what the last run said
```

Every four hours, jittered. A use-count moves in hours, so this keeps the curve
honest rather than chasing latency, and six browser loads a day does not look
like a scraper.

## When it breaks, it says so — and only then

The worker exits non-zero when a sound **that was being read until recently**
stops reading. `OnFailure` in the unit file turns that into a notification. This
matters more than it sounds: the audio tracker failed silently for weeks,
because a job that fails and says nothing looks exactly like a job with nothing
to do.

The qualifier is doing real work. A sound with no reading in the last 30 days is
reported as `skip` and a warning, not a failure. The obvious rule — "did it ever
read?" — is wrong here, and this database is why: it carries three seeded sounds
(`7300001`, `7300002`, `7300003`) whose TikTok ids were invented, and the seeder
gave them seven snapshots apiece, all dated March 2026. By the ever-read test
they are regressions, so the job would exit non-zero on every single run
forever, which is the same as having no alert at all.

Those three rows are worth deleting from **Trackers → sounds** once you are
happy to — they are demo fixtures pointing at ids that will never resolve, and
until they go every run prints three `skip` lines. Nothing here depends on it;
the output is just quieter.

So a healthy run on a correctly-placed VPS reads `Wherever I Go`, prints three
`skip` lines for the fixtures, and exits 0.
